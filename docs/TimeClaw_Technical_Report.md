## 1. 项目概述

TimeClaw 是一个**原生多模态时序自主 Agent 平台**，借鉴 OpenClaw 在通用 Agent 领域的核心思想（自主推理、工具编排、分层记忆、经验自进化），将其迁移并重新设计用于**时间序列分析与预测**这一全新领域。

TimeClaw 不是一个单一的预测模型，而是一个**时序领域的自主 Agent 操作系统**——它以 LLM 为推理核心，动态调度 62 个专业原子工具和 4 个时序基座模型，通过 ReAct 推理循环逐步求解复杂的多模态时序任务。

### 核心能力矩阵

| 维度 | 能力 |
|------|------|
| **任务覆盖** | 预测（forecast）、趋势分类（trend）、技术指标预测（indicator）、多选题 QA（MCQA）、新闻-价格相关性分析（correlation） |
| **模态支持** | 数值时间序列、文本报告/新闻、图像/图表（预留声音扩展接口） |
| **数据域** | 气象（Weather）、金融（Finance），架构支持任意领域扩展 |
| **推理范式** | 基于证据的反思式 ReAct（Evidence-Grounded ReflAct） |
| **学习机制** | 六层文件制自进化记忆，支持训练-蒸馏-测试闭环 |

## 2. 研究动机与问题定义

### 2.1 时序分析面临的核心挑战

传统时序预测的范式是"**一个模型解决一切**"——为每个数据集训练一个独立模型（或使用一个通用基座模型），然后直接输出预测值。这种范式在以下场景中表现乏力：

```
┌──────────────────────────────────────────────────────────┐
│           传统范式难以应对的现实场景                         │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 分布漂移 (Distribution Drift)                        │
│     → 训练时的数据分布 ≠ 推理时的数据分布                   │
│     → 例：突发疫情/战争导致金融数据规律性断裂                │
│                                                          │
│  2. 变量异质性 (Variable Heterogeneity)                   │
│     → 同一数据集中不同通道的统计特性差异巨大                 │
│     → 例：32通道工业传感器数据，温度/压力/流量各异           │
│                                                          │
│  3. 多模态融合决策 (Multimodal Decision)                  │
│     → 预测不仅依赖数值，还需理解文本语境                    │
│     → 例：天气预报+气象文本、股价+财经新闻                  │
│                                                          │
│  4. 模型版本爆炸 (Model Explosion)                        │
│     → 为 N 个数据集训练 N 个模型，维护成本不可控             │
│                                                          │
│  5. OOD 推理 (Out-of-Distribution)                       │
│     → 遇到从未见过的数据分布时，缺乏兜底机制                 │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 2.2 TimeClaw 的解题思路

> **核心思想**：不再试图用一个模型覆盖全集，而是构建一个"时序领域的自主 Agent"——它能**诊断数据特征**、**动态选择最合适的工具/模型组合**、**综合多模态证据进行推理**、**通过经验积累持续进化**。

这一思路直接借鉴了 OpenClaw 在通用 Agent 领域的成功范式，但需要面对时序领域特有的技术挑战。

## 3. 与 OpenClaw 的问题域差异分析

### 3.1 本质差异：从"会话交互"到"信号理解"

OpenClaw 和 TimeClaw 虽然共享 Agent 的核心思想，但面对的问题域存在**本质性差异**，这些差异从根本上驱动了架构设计的分化。

```
╔══════════════════════════════════════════════════════════════════════╗
║                    OpenClaw vs TimeClaw 问题域对比                   ║
╠═══════════════════╦══════════════════════╦════════════════════════════╣
║      维度          ║     OpenClaw          ║     TimeClaw              ║
╠═══════════════════╬══════════════════════╬════════════════════════════╣
║ 核心输入          ║ 自然语言文本          ║ 高维数值信号 + 文本 + 图像  ║
║ 交互模式          ║ 多轮对话（无状态感知） ║ 单次推理（全量数据感知）    ║
║ 推理目标          ║ 执行用户意图          ║ 预测/分类/决策              ║
║ 工具类型          ║ 通用（Shell/浏览器）   ║ 领域专用（统计/深度学习）   ║
║ 输出形式          ║ 自然语言/代码/动作    ║ 结构化数值/标签             ║
║ 验证标准          ║ 用户满意度            ║ 数学指标（MSE/MAE/Acc）     ║
║ 时间维度          ║ 弱（会话历史）        ║ 强（信号自身即时间函数）    ║
║ 数据精度要求      ║ 低（语义即可）        ║ 极高（小数点后4位有意义）   ║
║ 物理约束          ║ 无                    ║ 有（温度不能 <−273°C 等）   ║
║ 分布概念          ║ 不涉及                ║ 核心问题（漂移/异质性/OOD） ║
╚═══════════════════╩══════════════════════╩════════════════════════════╝
```

### 3.2 六个关键差异及其架构影响

#### 差异 1：输入模态——从"文本原生"到"信号原生"

**OpenClaw**：输入天然是 LLM 能理解的自然语言文本。Agent 直接处理文本 token。

**TimeClaw**：核心输入是**高维数值时间序列**（如 168 个时间步 × 1~32 通道），LLM 无法直接"看懂"一串浮点数的统计意义。

**架构影响** → 催生了 **TokenCast 信号原生编码系统** 和 **DataFingerprint 数据指纹**：

```
                 OpenClaw                          TimeClaw
                 ──────                            ────────
      用户消息 ──→ LLM 直接理解       数值信号 ──→ TokenCast 编码 ──→ 语义 Token
                                                 ├──→ DataFingerprint ──→ 模型路由
                                                 └──→ Profiling 工具 ──→ 统计摘要
```

TokenCast 通过 4 种量化策略（uniform/quantile/kmeans/adaptive）将连续信号映射为离散语义 Token，保留全量数值精度的同时让 LLM 能够"理解"信号特征。这是 TimeClaw 相比传统"时序转图像"方案的核心创新。

#### 差异 2：工具体系——从"通用执行"到"领域专家"

**OpenClaw**：工具是通用的——执行 Shell 命令、浏览网页、调用 API。工具之间基本独立，结果是自然语言描述。

**TimeClaw**：工具是**高度专业化的领域专家**——ARIMA 模型、STL 分解、Granger 因果检验、FFT 频谱分析等。工具之间有**强依赖关系**（如"先 detect_seasonality 检测周期 → 再 stl_decompose 用检测到的周期分解"），且输出是**结构化数值**（数组、矩阵、统计量）。

**架构影响** → 催生了 **ClawHub 分类工具库**（62 个原子工具，10 个类别）和 **Mini-ReAct 动态编排**：

```
     OpenClaw 工具链:  [Shell] → [浏览器] → [文件读写]     （工具间弱耦合）
                        ↓          ↓           ↓
                     文本结果    文本结果     文本结果

     TimeClaw 工具链:  [basic_stats] → [detect_seasonality] → [stl_decompose(period=N)]
                        ↓                    ↓                        ↓
                     {mean, std, ...}     period=24              趋势+季节+残差
                                             └──────→ 参数传递 ───→ ┘

     关键区别：TimeClaw 的工具输出直接作为下一个工具的输入参数，
              形成数据驱动的动态执行链。
```

#### 差异 3：验证标准——从"语义满意"到"数学精确"

**OpenClaw**：成功标准是用户是否满意，本质是**主观的语义评价**。

**TimeClaw**：成功标准是**客观的数学指标**——MSE、MAE、RMSE、MAPE（预测）、Accuracy（分类/选择题）。预测值偏差 0.1 度可能就决定了判断是否正确。

**架构影响** → 催生了 **SafeAuto 质量门控系统** 和 **双层自纠正机制**：

```
     OpenClaw:  LLM 输出 ──→ 用户看了满意 ──→ 结束

     TimeClaw:  Pipeline 输出
                    ├──→ [QualityGate] FOL 逻辑检查 ──→ 通过？
                    ├──→ [BoundCheck] 物理边界约束  ──→ 通过？
                    ├──→ [ConsistencyCheck] 历史一致性 ──→ 通过？
                    └──→ [_final_llm_call] 结构化纠正  ──→ 格式正确？
                            → 任一未通过 → 重分析 / LLM 复审
```

#### 差异 4：数据分布——从"无状态"到"分布感知"

**OpenClaw**：每次对话是独立的，不需要关心"输入数据的统计分布"。

**TimeClaw**：数据分布是**核心问题**。同一种天气数据，热带和极地的分布完全不同；同一只股票，牛市和熊市的统计特征天差地别。Agent 必须先**诊断数据分布**，再决定使用哪个模型/工具。

**架构影响** → 催生了 **DataFingerprint 指纹系统** 和 **FingerprintMatcher 模型路由**：

```
     原始数据 ──→ FingerprintExtractor
                    ├─ BasicStats (均值/标准差/偏度/峰度)
                    ├─ Stationarity (ADF/KPSS 平稳性检验)
                    ├─ Trend (方向/斜率/显著性)
                    └─ AnomalyCount (异常点数量)
                         ↓
                    DataFingerprint
                         ↓
                    FingerprintMatcher
                    ├─ 匹配 SBM profile    → 选择最优基座模型
                    ├─ 匹配 Checkpoint     → 加载领域微调模型
                    └─ OOD Fallback        → SBM zero-shot + ARIMA + 逻辑约束
```

#### 差异 5：多模态交互——从"文本+视觉"到"信号+语义"

**OpenClaw**：多模态主要指文本+图像+语音的**人机交互界面**。

**TimeClaw**：多模态指的是**数值信号与文本语义的深度融合决策**。例如：给定一周的温度时间序列和一段暴风雪新闻，Agent 需要判断"新闻描述的事件是否已经反映在数值数据中"——这需要**跨模态因果推理**。

**架构影响** → 催生了 **多模态对齐-检测-融合三层架构** 和 **跨模态一致性检查**：

```
     ┌─────────────┐     ┌─────────────┐     ┌───────────────┐
     │ 时间序列模态  │     │  文本模态    │     │  图像模态      │
     │ (数值信号)    │     │ (新闻/报告)  │     │ (图表/照片)    │
     └──────┬──────┘     └──────┬──────┘     └───────┬───────┘
            │                    │                     │
            ▼                    ▼                     ▼
     ┌──────────────────────────────────────────────────────┐
     │              ModalityDetector 模态检测                │
     │         自动识别输入中包含哪些模态                      │
     └──────────────────────┬───────────────────────────────┘
                            ▼
     ┌──────────────────────────────────────────────────────┐
     │              ModalityAligner 时间对齐                 │
     │         将文本/图像按时间戳对齐到时间序列轴              │
     └──────────────────────┬───────────────────────────────┘
                            ▼
     ┌──────────────────────────────────────────────────────┐
     │          Cross-Modal Consistency Check                │
     │   LLM 判断：文本描述的事件是否已在数值中体现？           │
     │        → already_in_data = True/False                │
     │        → 避免对同一事件影响"双重计算"                   │
     └──────────────────────┬───────────────────────────────┘
                            ▼
     ┌──────────────────────────────────────────────────────┐
     │              ModalityFusion 融合                      │
     │    策略: confidence_weighted / llm_arbitrated         │
     │    权重 = base_weight × 模态执行置信度                 │
     └──────────────────────────────────────────────────────┘
```

#### 差异 6：学习目标——从"偏好对齐"到"因果归因"

**OpenClaw**：通过 RL 从用户反馈中学习**偏好对齐**（用户喜欢什么样的回答风格）。

**TimeClaw**：通过记忆蒸馏学习**因果归因**（"为什么 ARIMA 在非平稳数据上失败？因为数据有强趋势，应该先差分或用 Prophet"）——这是**领域专家知识**的积累，而不是风格偏好。

**架构影响** → 记忆系统的蒸馏目标从"行为偏好"转向"工具-场景-因果"三元组：

```
     OpenClaw 记忆蒸馏:
         L1 (会话日志) → L2 (行为偏好) → L3 (人格特质)

     TimeClaw 记忆蒸馏:
         L1 (Notes: 工具链+评估指标)
             → L2 (MEMORY: "当数据 Hurst 指数 > 0.7 时，Chronos 优于 ARIMA")
             → L2 (TOOLS: "sentiment 工具对教育性文章易误判为 neutral")
             → L3 (PRINCIPLES: "先诊断后预测；多工具交叉验证")
             → L3 (PLAYBOOKS: "weather_forecast 标准 SOP: stats→trend→seasonality→SBM→ensemble")
```

| 如果直接照搬 OpenClaw… | 会出现的问题 | TimeClaw 的解法 |

## 6. 核心子系统详解

### 6.1 LLM 路由与调用层

```
timeclaw/llm/
├── base.py     (528 行)  — LLMBackend: 统一 LLM 后端
└── router.py   (83 行)   — ModelRouter: 按角色分配模型
```

**设计要点**：

- **双通道调用策略**：对自定义 `api_base` 的 `openai/` 前缀模型使用原生 OpenAI SDK（避免 LiteLLM 在某些代理上的响应损坏），其余走 LiteLLM 统一路由
- **指数退避重试**：对 429/502/503/timeout 自动重试，最多 5 次（2s → 4s → 8s → 16s → 32s）
- **流式降级**：非流式请求失败时自动降级为流式模式，收集 chunk 重组为完整响应
- **模型回退链**：主模型 → fallback_model，确保单点故障不中断流水线
- **三级 JSON 提取**：直接解析 → Markdown 代码块 → 大括号/方括号深度匹配
- **按角色分配**：支持为 manager/analyzer/executor/reasoner/text_light/text_heavy 分配不同模型，兼顾成本与能力

### 6.2 Pipeline 运行器

```
timeclaw/pipeline/
└── runner.py   (733 行)  — PipelineRunner: 端到端推理引擎
```

PipelineRunner 是 TimeClaw 的中枢，编排整个推理过程：

| 阶段 | 内容 | LLM 参与 |
|------|------|----------|
| Preprocess | 模态检测、指纹提取、5 项 Profiling | ✗ 纯确定性 |

## 7. 推理引擎与工具编排

### 7.1 Mini-ReAct 循环

TimeClaw 的核心推理采用 **Mini-ReAct**（Reasoning + Acting）范式，而非预先规划整条工具链：

```
                    ┌────────────────────────────────┐
                    │       ExecutorAgent             │
                    │       ReAct 循环                │
                    │                                │
                    │  ┌──────────────────────────┐  │
         step 1 →   │  │ Think: 数据有强趋势，     │  │
                    │  │   需要先确认季节性         │  │
                    │  │ Act: detect_seasonality()  │  │
                    │  │ Observe: period=24          │  │
                    │  └──────────────────────────┘  │
                    │              ↓                  │
                    │  ┌──────────────────────────┐  │
         step 2 →   │  │ Think: 有日周期=24，      │  │
                    │  │   用 STL 分解              │  │
                    │  │ Act: stl_decompose(p=24)   │  │  ← 参数来自 step 1
                    │  │ Observe: 趋势+季节+残差    │  │
                    │  └──────────────────────────┘  │
                    │              ↓                  │
                    │  ┌──────────────────────────┐  │
         step 3 →   │  │ Think: 残差较平稳，       │  │
                    │  │   用 Chronos 零样本预测    │  │
                    │  │ Act: chronos2_forecast(h=24)│  │
                    │  │ Observe: [15.1, 14.8, ...] │  │
                    │  └──────────────────────────┘  │
                    │              ↓                  │
                    │  ┌──────────────────────────┐  │
         step N →   │  │ Think: 已有充足证据       │  │
                    │  │ Act: done                  │  │
                    │  │ Answer: {forecast: [...]}  │  │
                    │  └──────────────────────────┘  │
                    │                                │
                    └────────────────────────────────┘
```

### 7.2 子 Agent 并发

对于复杂的多模态任务，ExecutorAgent 可通过 `spawn_subagent` 工具生成**最多 4 个并行子 Agent**，每个子 Agent 运行独立的 mini-ReAct 循环（最多 5 步），处理不同的分析子任务，最终由主 Agent 汇总结果。

### 7.3 ReasonerAgent 仲裁

ExecutorAgent 产出原始结果后，ReasonerAgent 执行：

1. **多模态后期融合**：基于各模态执行置信度加权平均
2. **跨模态一致性检查**：LLM 判断文本事件是否已在数值中反映（`already_in_data` 标记）
3. **LLM 综合合成**：综合全部模态证据产出最终答案
4. **SafeAuto 质量门**：多重确定性检查（边界、一致性、FOL 逻辑）

## 10. TokenCast 信号原生编码

### 10.1 设计理念

传统方案将时间序列转换为图像（如线图/热力图），再用视觉 LLM 分析。这种"非原生"方案存在严重的精度损失和高维干扰问题。

TimeClaw 采用 **TokenCast 信号原生编码**——直接将连续数值信号映射为离散语义 Token：

```
  连续信号:  [15.2, 14.8, 13.9, 12.1, ...]
                    ↓ 量化
  Token ID:  [847, 831, 814, 782, ...]
                    ↓ 词表映射
  语义表示:  [BOS, temp_warm, temp_warm, temp_mild, temp_cool, ..., EOS]
```

### 10.2 四种量化策略

| 策略 | 原理 | 适用场景 |
|------|------|----------|
| Uniform | 等宽分箱（linspace） | 均匀分布数据 |
| Quantile | 等频分箱（percentile） | 偏态分布数据 |
| KMeans | 1D K-means 聚类 | 多模态分布数据 |
| Adaptive | 密度自适应分箱（√density 分配 bin） | 通用场景 |

### 10.3 高级特性

- **多粒度编码**：同时生成粗粒度（64 bins）和细粒度（1024 bins）Token
- **通道感知编码**：多变量数据的每个通道使用独立量化器
- **特殊 Token 系统**：PAD(0), BOS(1), EOS(2), UNK(3), MASK(4)
- **双向映射**：编码（value→token）+ 解码（token→value），支持平滑重建

```
  │  存储: notes/<scope>.md  索引: SQLite 向量存储                  │
  ├─────────────────────────────────────────────────────────────────┤
  │  Layer 2: MEMORY.md (LLM 蒸馏，按 domain_task 分区)            │
  │  因果洞察: "当 Hurst>0.7 时，Chronos 优于 ARIMA，因为..."       │
  │  触发条件: 每 10 条新 Daily Note 触发蒸馏                       │
  ├─────────────────────────────────────────────────────────────────┤
  │  Layer 2': TOOLS.md (LLM 蒸馏)                                 │
  │  per-tool 使用经验: "sentiment 对教育性文章易误判 neutral"       │
  │  工具使用计数 + 数据不足标记                                    │
  ├─────────────────────────────────────────────────────────────────┤
  │  Layer 3: PRINCIPLES.md (LLM 蒸馏，最多 6 条)                  │
  │  跨域通用策略: "先诊断后预测；多工具交叉验证；文本可能过时"       │
  │  触发条件: 每 20 条 MEMORY insight 触发蒸馏                     │
  ├─────────────────────────────────────────────────────────────────┤
  │  Layer 3': PLAYBOOKS/ (LLM 蒸馏，按场景)                       │
  │  SOP: "weather_forecast: stats→trend→season→SBM→ensemble→gate"  │
  │  每个 (domain, task) 独立一份操作手册                            │

  蒸馏链:
      Notes ──→ MEMORY.md ──→ PRINCIPLES.md
                  └──→ TOOLS.md       └──→ PLAYBOOKS/
```

## 12. 质量保障与 SafeAuto

### 12.1 双层自纠正机制

```
  第一层：Pipeline 内部（确定性检查）
  ────────────────────────────────────
  ┌─────────────────────────────────────┐
  │ QualityGate                         │
  │ ├─ FOL 逻辑检查 (一阶逻辑谓词)      │
  │ ├─ BoundCheck (np.clip 物理边界)    │    温度 ∈ [-50, 60]°C
  │ ├─ ConsistencyCheck (5σ 偏差检测)   │    预测均值不偏离历史 5 倍标准差
  │ └─ ConstraintCheck (用户自定义)     │
  └─────────────────────────────────────┘
                    ↓ 未通过
  ┌─────────────────────────────────────┐
  │ LLM 复审 (_llm_verify)             │
  │ "检查有 X 项未通过，预测是否仍可信？" │
  └─────────────────────────────────────┘

  第二层：评估外层（结构化纠正）
  ────────────────────────────────────
  ┌─────────────────────────────────────┐
  │ _final_llm_call                     │
  │ Pipeline 原始输出 + 上下文           │
  │  → 结构化 JSON: {"answer": "A"}    │
  │  → 格式校验 + 语义校验              │
  │  → 自动重试（最多 2 次）             │
  └─────────────────────────────────────┘
```

### 12.2 多模态质量评估

```
  置信度 = 0.4 × 工具成功率 + 0.3 × 观察丰富度 + 0.3 × 预测质量

  工具成功率:  成功执行的工具 / 总调用工具
  观察丰富度:  返回有意义结果（>10字符）的工具 / 总工具
  预测质量:    预测结果是否合理（无 NaN/Inf，类型正确）
```
